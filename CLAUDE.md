## 1. Descripción y objetivo

Detector de objetos SSD-MobileNetV2 entrenado **desde cero** (`weights=None`; nunca descargar ImageNet) para 5 clases (`boligrafo, laptop, libro, moneda, mouse`), exportado a TFLite para integrarlo después en una aplicación móvil (RA). Proyecto escolar de Inteligencia Artificial. Meta de la etapa actual **[bitácora]**: mAP@0.5 ≥ 0.50. Problema principal actual: **baja fiabilidad de los resultados del entrenamiento**, cuya causa se está investigando sistemáticamente (anotaciones, dimensiones y solapes de cajas, distribución de datos); no se presupone que los labels sean la causa.

## 2. Arquitectura y estructura del repositorio

Todo se deriva de `config.py`: editar `CLASES` (el índice = id de clase en los `.txt` YOLO) cambia `NUM_CLASES`, `labels.txt` y las cabezas del modelo. En el modelo el índice 0 es **fondo**; las clases son 1..N.

Pipeline (archivos acoplados por la geometría de anchors):
- `config.py`: `IMG_SIZE=256` fijo; mapas de características 16, 8, 4, 2, 1 (strides 16–256), `ANCHORS_POR_CELDA=6`, `ESCALA_MIN=0.07` → **2046 anchors** (341 celdas × 6). Cambiar `IMG_SIZE` rompe `model.py`/`anchors.py` (hay un `assert`).
- `anchors.py`: anchors por celda con ratios 1:1, 1:1 intermedio, 2:1, 1:2, 3:1, 1:3; codificación/decodificación con `VARIANZAS`; IoU.
- `data.py`: lee YOLO de `data/{train,val}/{images,labels}` (imagen sin `.txt` = solo fondo; `MAX_CAJAS=20`). Carga (`_cargar_imagen`): `tf.io.decode_image(channels=3)` → **orientación EXIF (E1, solo si `APLICAR_EXIF=1`; `_leer_orientacion`, `_orientaciones`, `_aplicar_orientacion`, 8 orientaciones, antes del resize)** → `tf.image.resize` a 256×256 (bilineal, sin antialias, sin conservar proporción) → `/255`. `construir_dataset` (train/val) y `dataset_solo_imagenes` (evaluación) comparten esa carga. Después: `tf.data`, aumentos solo en train (flip, `_random_zoom` p=0.5 recorte 0.60–0.90, brillo, contraste) y asignación de anchors (IoU ≥ 0.5 + mejor anchor por GT) dentro del pipeline: el modelo recibe targets ya codificados `[A,5]`.
- `model.py`: MobileNetV2 sin pesos + 3 bloques extra + cabezas separables de caja y clase; la normalización [0,1]→[-1,1] va dentro del modelo. `construir_modelo_inferencia` añade decodificación y softmax.
- `losses.py`: `perdida_ssd` = Smooth L1 + CE con hard negative mining 3:1.
- `train.py`: Adam, `ModelCheckpoint` (val_loss) → `salida/best_model.keras`, `ReduceLROnPlateau(patience=5, factor=0.5)`, `EarlyStopping` (paciencia `config.PACIENCIA`=30), `CSVLogger` → `salida/historial.csv`. Sobrescribe `C.BATCH_SIZE` desde CLI antes de construir el dataset.
- `evaluate.py`: NMS por clase y mAP@0.5 propios (carga con `compile=False`, así que no necesita registrar la pérdida). `export_tflite.py`: el NMS **no** va en el grafo; la app lo aplica (score ≥ 0.5, IoU ≤ 0.45). Salidas TFLite: `boxes [1,2046,4]` (ymin,xmin,ymax,xmax) y `scores [1,2046,6]`, identificadas por shape, no por orden.
- Utilidades: `recalibrar_bn.py` (E6a: recalibra las estadísticas móviles de BN de un checkpoint y guarda uno derivado; ver sección 5), `verificar_dataset.py` (conteos), `repartir_recursos.py` (Recursos/ → data/), `generar_dataset_sintetico.py` (solo prueba de pipeline).
- Otros: `archivo/best_m1..m4.keras` (checkpoints archivados; m4 = Run 3, en `archivo/`, no en `salida/`) y los archivos del **Run 5** (E1): `archivo/best_m5.keras` (= `salida/best_model.keras`, SHA256 `0f092594775bc95980befcbee367046c91e7a0fdfcd9236506153607ead93526`), `archivo/historial_m5.csv` y `archivo/evaluate_m5.txt`; **Run 6** (E6b-EXIF): `archivo/best_m6.keras` (= `salida/best_model.keras` hasta el Run 7, SHA256 `24b06622…99d73`), `historial_m6.csv`, `evaluate_m6.txt`, `best_m6_bnrecal.keras` y `evaluate_m6_bnrecal.txt`. Convención: el sufijo `_mN` identifica el run; archivar antes de volver a entrenar (`train.py` sobrescribe `salida/best_model.keras` e `historial.csv`). El `best_m5.keras` anterior (Run 4, SHA256 `bb30e9fd…cbba8`) quedó sobrescrito por indicación del usuario y es recuperable en el commit `794a049`. `salida/` (ignorada por git), `Recursos/` (origen de fotos, vacío tras repartir), `tests/test_exif.py` (tests de E1 y de Pillow condicional), `diagnostico/run5/` (scripts y salidas de los diagnósticos de solo lectura posteriores al Run 5; ver bitácora §14), guías `GUIA*.md`.

## 4. Configuración y funcionamiento general

```bash
python verificar_dataset.py                 # imágenes/cajas por clase en train y val
python repartir_recursos.py [--mover]       # Recursos/ -> data/{train,val}, patrón 3-1,4-1
python train.py --epocas 150 [--batch N --lr X --paciencia N]
python evaluate.py [--modelo RUTA --score 0.5]   # Precision, Recall, mAP@0.5 sobre val
python export_tflite.py --cuantizar         # salida/detector.tflite + labels.txt
```

Con GPU: entrenar desde WSL2 y preferiblemente con el proyecto en ext4, no en `/mnt/...` (ver `GUIA_REENTRENAMIENTO_WSL.md`). Los hiperparámetros por defecto viven en `config.py`. **Los entrenamientos los ejecuta únicamente el usuario (ver 9.7).**

**Orientación EXIF (`APLICAR_EXIF`)** — desactivada por defecto (modo *legacy*); se activa con la variable de entorno y **debe usarse igual al entrenar y al evaluar** (ejecutados por el usuario desde WSL2):
```bash
APLICAR_EXIF=1 python train.py --epocas 150      # entrenar con EXIF
APLICAR_EXIF=1 python evaluate.py --score 0.5    # evaluar el modelo entrenado con EXIF
python -B -m unittest tests.test_exif -v         # 15 tests de E1 y de Pillow condicional (no entrenan; tardan ~30 s)
python -B -m unittest tests.test_recalibrar_bn -v  # 16 tests de la recalibración de BN (E6a; no entrenan; ~70 s)
python -B -m unittest tests.test_bn_momentum -v      # 12 tests del momentum de BN del backbone (E6b) y de --semilla (no entrenan)
BN_MOMENTUM_BACKBONE=0.99 python train.py --epocas 150 --semilla 42   # E6b (lo ejecuta el usuario; sin la variable = 0.999 legacy)
```
Evaluar con la bandera desactivada un modelo entrenado con ella (o al revés) usa un marco de entrada distinto y los resultados **no son válidos**. La bandera no se guarda con el modelo (por ahora no se añade infraestructura de configuración por run).

## 6. Decisiones técnicas consolidadas (respetar)

- Entrenar desde cero (`weights=None`); no usar `imagenet` sin que el usuario lo confirme (ver pendientes).
- `IMG_SIZE=256`, 6 anchors/celda, escala mínima 0.07, `CLASES` en orden alfabético, fondo = índice 0.
- Reparto train/val en bloques consecutivos 3-1/4-1 (evita fuga de datos entre fotos de una ráfaga); no cambiarlo por split aleatorio.
- NMS fuera del grafo TFLite; entrada [0,1], normalización dentro del modelo.
- Entrenamiento en WSL2; `EarlyStopping` paciencia 30.

## 7. Problemas conocidos y limitaciones

- **[verificado]** `val_loss` mejora entre runs pero el mAP no (0.065 → 0.061 → 0.055): pérdida y métrica no están alineadas.
- **[verificado] Desajuste de orientación EXIF (hallazgo principal de la auditoría 1):** las etiquetas de varias imágenes están dibujadas sobre la foto con la orientación EXIF aplicada, pero `data.py` (`tf.io.decode_image`, que devuelve píxeles crudos sin rotar; comprobado con TF 2.21) carga la imagen sin rotar, así que la caja no cae sobre el objeto. Comprobado visualmente en moneda_162, 175, 198, 199 (EXIF 6/8/3) y laptop_113/128 (EXIF 3). Censo de metadatos sobre las 1410 imágenes: orientación 3/6/8 en 177 de 300 de moneda y 70 de 263 de laptop (247 en total, 17.5 %); bolígrafo, libro y mouse no tienen. `evaluate.py` usa la misma carga, por lo que la validación de esas clases también está afectada. Imágenes sin EXIF (o 1) inspeccionadas: cajas correctas. **Estado: corregido en el código bajo la bandera `APLICAR_EXIF` (E1, ver sección 5); los 4 runs históricos y el modo legacy siguen afectados.** Auditoría 2: las etiquetas están en el marco orientado en las 247 imágenes (143 de moneda con EXIF 6/8 cumplen la prueba de aspecto; revisión visual de las 247 sin excepciones); las cajas afectadas son 560 de 2,798 (moneda 63–64 %, laptop 26–28 %, en train y en val). Que esto explicara el AP ≈ 0 de moneda es una hipótesis **de nuevo plausible**: la medición del Run 5 la desmentía, pero estaba distorsionada por BN; con BN recalibrado moneda tiene AP 0.334 con EXIF (Run 5, época 8) frente a 0.032 sin EXIF (Run 4, época 11). Aún no aislado (checkpoints de runs y épocas distintos).
- **[verificado]** La bitácora afirma que las monedas miden < 12 px a 256×256 partiendo de fotos de 2048×1536; los datos no lo respaldan (hay fotos de 4032×3024 y las cajas, en el marco orientado, tienen mediana ≈ 60 px). Esa explicación queda en duda.
- **[verificado, auditoría 3] Pipeline de datos**: sin otros errores de coherencia píxel–caja (codificación ida y vuelta exacta; flip y zoom con IoU ≥ 0.886 en prueba sintética); train y val usan el mismo código de carga. Hallazgos pendientes (no corregidos, no autorizados): (a) cobertura de anchors débil en bolígrafo: 37 % de sus GT sin ningún anchor con IoU ≥ 0.5 y 61 % con ≤ 2 (moneda: 15 % y 52 %); (b) 138 GT comparten su mejor anchor con otro GT (58 imágenes, todas de bolígrafo); la asignación usa `tensor_scatter_nd_update` con índices repetidos, pero en CPU es **determinista (gana el último GT)** [verificado, Windows TF 2.21.0; no confirmado en WSL2]; (c) `_random_zoom` descarta ≈ 9.0 % de los GT cuando se aplica (≈ 4.5 % por época; siempre centro fuera del recorte) y **0 % con ≥ 50 % del objeto visible** [verificado con el código real; corrige la estimación 14 %/4.9 %]; (d) `tf.image.resize` sin antialias y sin conservar proporción; (e) el entorno WSL2 usa TF 2.22.0rc1 y Keras nightly sin versiones fijadas.
- **[verificado]** Bolígrafo: en las 5 imágenes de la muestra hay solapes importantes entre cajas (IoU hasta 0.72), debidos a bolígrafos amontonados en diagonal con cajas alineadas a los ejes; no son errores de etiquetado. **[hipótesis]** Pares con IoU > 0.5 pueden dar ambigüedad al reparto de anchors y al NMS (0.45).
- **[verificado, solo muestra]** Los labels de laptop, libro y mouse sin EXIF no mostraron anomalías numéricas; no se inspeccionaron visualmente la mayoría (no extrapolar a todo el dataset).
- **[verificado]** El 52 % de las cajas de bolígrafo tienen relación de aspecto > 2.5.
- **[hipótesis]** Cajas de bolígrafos diagonales incluyen mucho fondo (alineadas a los ejes; en las 4 imágenes inspeccionadas se ajustan razonablemente, con algo de holgura). La hipótesis de la bitácora de objetos secundarios sin etiquetar aprendidos como fondo pierde fuerza: cada imagen contiene solo una clase y no se vieron objetos sin anotar en lo inspeccionado; `ReduceLROnPlateau(patience=5)` estrangula el LR (visto en Run 4, LR hasta 1.56e-5, sin historial que lo confirme).
